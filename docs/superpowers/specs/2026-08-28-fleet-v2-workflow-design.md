# Fleet v2 — workflow layer design

Date: 2026-08-28. Status: draft for operator review.

## Why

A/B run on 2026-08-28: the same GUI task took a single Fable turn 3m51s (verified) and the
v1 fleet ~46 min. The fleet's minutes went to: 12 waiting on human keypresses (10 permission
prompts + 1 question), 12 high-effort thinking before the first file, 6 hop latency (turns
ending with nothing to wake the thread), 5 recalibration, 7 actual work. The design produced
by opus was better than the single-turn prototype; the process around it was the cost.

v2 targets the process: no human-gated stalls in unattended lanes, effort set per task not
per thread, synchronous tool-tier calls, and packets that are cheap to read and parse.

## Scope

- A parallel profile in the same repo (`[profile.v2]` in `fleet.toml`, tmux session `fleet2`,
  thread names suffixed `2`: `sonnet2`, `opus2`, `haiku-fs2`, `haiku-router2`). v1 keeps
  running untouched until v2 wins the A/B.
- New verbs: `fleet ask`, `fleet send --effort/--lane/--reply/--done`, `fleet decide`.
- Three fleet hooks installed per-thread via `--settings` (merging with the operator's
  global hooks, which stay): `router` (UserPromptSubmit), `gate` (PreToolUse), `hold`
  (Stop), plus `perm` (PermissionRequest).
- Two dashboard widgets in `gui/widgets/`: `prompts` (pending permission prompts with
  Proceed/Deny) and `hooks` (hook decision tail). Built on the fleet GUI (`gui/`, opus
  design), not on `gui-fable/`.

Out of scope: changing model choices, the ledger format beyond new event kinds, the v1
briefs (v2 gets its own under `briefs/v2/`).

## Section 1 — Packets

Compress coordination, never content. A packet is a fixed 3-line header + free body.

```
@to sonnet2  @from operator  @lane build  @effort med  @reply file
@refs <ROOT-relative paths, space separated>
@done <one-line acceptance test>
<body>
```

Fields:

| field | values | default | meaning |
|---|---|---|---|
| `@to` / `@from` | thread name / `operator` | required | routing + ledger attribution |
| `@lane` | `lookup` `build` `plan` `judge` `consult` | router's verdict | picks target, effort, permission tier (table in §4) |
| `@effort` | `low` `med` `high` | lane default | applied via `/effort` before paste |
| `@reply` | `inline` `file` `none` | `file` for build/plan/judge; `inline` for lookup | how the answer comes back |
| `@refs` | paths | empty | replaces pasted context |
| `@done` | text | required for build/plan | what "finished" means; `gate` refuses packets without one |
| `@id` | ulid | generated by `fleet send` | correlates replies and hook events |

Replies carry `@from <thread> @re <id> @status done|blocked|partial @out <path or ->` on line 1,
then prose. `@status blocked` must name what it needs.

Lanes:

| lane | target | effort | perm tier | reply |
|---|---|---|---|---|
| lookup | haiku-fs2 (sync via `fleet ask`) | low | bypass | inline |
| build | sonnet2 | med | acceptEdits | file |
| plan | opus2 | high | acceptEdits | file |
| judge | fresh non-fork agent (haiku or sonnet) | med | bypass | file |
| consult | fable (dormant; operator wakes) | high | acceptEdits | file |

Router: `haiku-router2` gets the body + `briefs/v2/router.md` (a ~10-line rubric with
examples), returns exactly one header line `@lane X @effort Y @target Z`. Sonnet2 may
override with `@override <reason>`; overrides are ledgered for rubric tuning. Sonnet2 may
also call the router itself mid-task (`fleet ask haiku-router2 "..."`) when splitting work.

Handoff files stay verbose — they are read cold. They are written once and referenced via
`@refs`, never pasted.

## Section 2 — Synchronous tool tier and enforcement hooks

### `fleet ask <thread> "<body>"`
Pastes `@to <thread> @from <caller> @lane lookup @reply inline` + body, then tails the
target's pane until a reply header `@re <id>` appears (or the pane returns to prompt with a
`⏺` block after the paste), and prints the reply to stdout. Timeout 30 s → exit 3 with the
last 20 pane lines. Measured haiku round-trip: 1.5 s. Callers get the answer as a tool
result inside the same turn — nothing to wait for, no cross-session message.

`fleet ask` is allowed in every tier's settings. The v1 `SendMessage` route to haiku-* is
blocked by `gate` with the message "use `fleet ask`".

### Hooks (all shell, `jq`-based like the operator's existing hooks; each ≤ 3 s except `perm`)

| hook | event | does | on failure |
|---|---|---|---|
| `router` | UserPromptSubmit | if the prompt is a packet without `@lane`, calls `fleet ask haiku-router2` and injects `[router] @lane … @effort … @target …` as context | no injection; sonnet routes unaided |
| `gate` | PreToolUse (SendMessage, Bash `fleet send`) | blocks (exit 2) sends to opus2/fable unless lane is plan/consult or `@override` present; blocks build/plan packets without `@done`; blocks SendMessage to haiku-* | falls open (allow) — a gate outage must not stall |
| `hold` | Stop | if `state/v2/pending/<thread>.json` lists an `@reply inline` packet this thread sent and no `@re` arrived, blocks the stop with "reply from X pending — `fleet ask` is synchronous; poll or mark abandoned with `fleet miss`" | falls open |
| `perm` | PermissionRequest | see §3 | falls through to the normal prompt |

Every hook writes a ledger event `{"ev":"hook","hook":..,"thread":..,"decision":"allow|block|inject|allow-auto|deny|escalate","ms":..,"why":..}`.

## Section 3 — Permission hook and the `prompts` widget

Tier policy (`settings/v2/<tier>.json`, referenced from each thread stanza):

| tier | permission_mode | perm hook behaviour |
|---|---|---|
| tool (haiku-*) | bypassPermissions | n/a; `guard-destructive.sh` + deny list (`curl -X POST|PUT`, `ssh`, `git push`, `rm -rf` outside `state/`) still apply via PreToolUse |
| expert (forks) | bypassPermissions | as tool; `dirs` limited to the packet's `@refs` dirs + ROOT |
| warm (opus2) / hot (sonnet2) | acceptEdits | `perm` hook decides Bash prompts |

`perm` decision procedure, in order:
1. Command matches the destructive/egress deny regex → `deny`, ledger, done.
2. Every path token in the command resolves under ROOT or `/tmp` and no deny match →
   `allow-auto`, ledger. (Expected to cover all 10 of the 2026-08-28 prompts.)
3. Otherwise → write `state/v2/prompts/<thread>-<id>.json` `{thread, tool, command, cwd, t}`,
   ledger `escalate`, then poll that file every 0.5 s for a `decision` field, up to 240 s
   (under the 300 s hook timeout). `allow`/`deny` → return it. Timeout → remove the file
   and fall through to the normal prompt.

`fleet decide <thread> <id> allow|deny` writes the decision field. The `prompts` widget
(`gui/widgets/prompts/`, `WATCH state/v2/prompts/*.json`) renders one card per pending file
with the exact command and two 44-px buttons that `POST /w/prompts/decide`. A third button,
**keypress**, sends `tmux send-keys <n>` for the prompts hooks cannot intercept
(AskUserQuestion, a timed-out perm prompt); the card shows the pane's last 12 lines so the
operator sees what the keypress answers.

`hooks` widget (`WATCH ledger/events.jsonl`): tail of `ev:hook` events, red row on `block`
or `escalate` older than 60 s, per-thread counts for the day.

## Section 4 — Profile layout and the A/B test

`fleet.toml`:

```toml
[profile.v2]
session = "fleet2"
briefs = "briefs/v2"

[profile.v2.thread.sonnet2]
model = "claude-sonnet-5"; tier = "hot"; effort = "med"
settings = "settings/v2/hot.json"; baseline = ["briefs/v2/sonnet.md"]
[profile.v2.thread.opus2]
model = "claude-opus-5"; tier = "warm"; effort = "high"; forkable = true
settings = "settings/v2/warm.json"; baseline = ["briefs/v2/opus.md"]
[profile.v2.thread.haiku-fs2]
model = "claude-haiku-4-5"; tier = "tool"; effort = "low"; persist = "respawn"
settings = "settings/v2/tool.json"; baseline = ["briefs/v2/haiku-fs.md", "maps/projects.md", "maps/conventions.md"]
[profile.v2.thread.haiku-router2]
model = "claude-haiku-4-5"; tier = "tool"; effort = "low"; persist = "respawn"
settings = "settings/v2/tool.json"; baseline = ["briefs/v2/router.md"]
```

`fleet --profile v2 <verb>` (env `FLEET_PROFILE=v2` equivalent). Registry entries carry
`profile`; `status` shows both profiles, grouped. Existing tests keep passing with no
profile given (v1 is the implicit default profile).

Briefs under `briefs/v2/` restate the protocol in packet terms: `_protocol.md` (packets,
lanes, `fleet ask`, "servable before consulting", `@done` is the contract), one role brief
per thread, `router.md` rubric.

A/B protocol: same packet to v1 `sonnet` and v2 `sonnet2` (different target dir), measure
wall-clock to `@done`, ledger `$`, count of `escalate` and `block` events, operator
keypresses. Task 1 is a re-run of the GUI slice-2 packet (workspace widget). Success bar for
v2 to replace v1: ≤ 2× the single-turn time on a build-lane task with zero operator
keypresses, and no drop in the judge lane's verdict on output quality.

## Testing

- Unit: packet parse/format round-trip; lane table lookup; `perm` decision procedure on the
  10 recorded 2026-08-28 commands (all `allow-auto`) plus deny cases; `fleet ask` against a
  fake tmux pane fixture (existing tests already stub tmux).
- Hook scripts: bats-style shell tests feeding recorded hook payloads, asserting exit code
  and ledger line.
- Live (skipped unless `fleet2` exists, like the current live tests): `fleet ask haiku-fs2`
  round-trip < 5 s; `perm` escalate → `fleet decide` → command runs.

## Risks

- Hook timeouts: `perm` holds a request thread for up to 240 s; only one pending prompt per
  thread is possible anyway (the thread is blocked), so no pile-up.
- `bypassPermissions` on tool tier: bounded by `guard-destructive.sh`, the deny list, `dirs`,
  and git. Network egress is the residual risk; the deny regex covers `curl` writes and `ssh`.
- Router misclassification: sonnet2 overrides are one line and ledgered; the rubric is tuned
  from the override log, not guessed upfront.
